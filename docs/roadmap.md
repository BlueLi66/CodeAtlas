# CodeAtlas — AI 应用全栈学习路线

> 建立：2026-09-18  
> 当前阶段：大三上  
> 方向：AI 应用全栈工程（以可见、可交互的产品为中心）  
> 核心项目：**CodeAtlas — 代码库学习导航器**

---

## 一、路线选择

### 当前背景（只保留已确认信息）

- 计算机专业，大三上。
- 已学习操作系统、计算机网络、数据库的基础知识。
- 接触过 C++ WebServer 和 LevelDB；它们是后续学习与验证素材，但不作为当前主线项目或默认的已掌握能力。
- Python 处于入门阶段。
- 挑战杯项目已停止；没有 Dify 开源贡献。
- 更喜欢能看见结果、能直接感受到功能变化的开发工作。

### 为什么选择 AI 应用全栈

目标不是成为“只会调用模型 API 的人”，而是能够把 AI 能力做成可靠、可使用的产品：前端交互、后端服务、数据管理、检索、模型调用、测试与部署缺一不可。

这条路线具备两个优势：

1. **反馈快**：每周都会有页面、交互或产品能力的可见变化。
2. **可持续扩展**：后续可向 AI 平台、LLM 服务工程、检索系统，甚至推理部署延伸；已有的 C++/系统基础可成为差异化，而不必和主线竞争时间。

### 近期原则

```
单主线：CodeAtlas 项目驱动学习
先产品闭环，后高级能力
先直接 SDK 与基本原理，后框架封装
先可测试、可部署，后复杂功能
```

## 二、项目定义：CodeAtlas

### 一句话描述

CodeAtlas 帮助开发者理解陌生代码仓库：导入仓库后查看目录与代码、了解模块职责，并对代码提问；每个回答都应定位到具体源码片段。

### 目标用户

- 正在阅读陌生项目的学生或初级开发者。
- 希望系统梳理自己历史项目的开发者。

### 核心价值

不是泛泛地“和代码聊天”，而是提供：

- 仓库结构与模块职责的清晰概览；
- 有来源定位的代码问答；
- 可追踪的代码阅读与学习进度。

### MVP 范围（必须完成）

1. 上传 ZIP 格式的代码仓库。
2. 解析安全允许的文本源文件，展示目录树与文件内容。
3. 自动生成仓库概览和模块摘要。
4. 针对当前仓库提问，流式显示回答，并列出引用的文件与片段。
5. 保存仓库、文件元数据、对话和阅读进度。
6. 用 Docker Compose 一键启动，并有基础测试与 README。

### 明确不做（第一版）

- 自动修改或执行代码；
- 自动修复 Bug；
- 多 Agent；
- 多模型提供商切换；
- 完整调用图、复杂 AST 分析；
- 多人协作、权限体系、云端同步；
- Kubernetes、CUDA、推理引擎。

### 后续候选功能（仅在 MVP 完成后选择）

- Python/C++ 符号提取与轻量依赖图；
- “建议先读哪些文件”的学习路径；
- 基于仓库的面试题和复习卡片；
- 代码阅读笔记与待复习列表；
- 混合检索、检索评测与缓存。

## 三、最小技术栈

| 层级 | 技术 | 当前取舍 |
|---|---|---|
| 前端 | TypeScript + React + Vite | 优先建立可见交互；先不使用复杂状态库或 SSR |
| 后端 | Python + FastAPI + Pydantic | REST API、文件上传、流式响应 |
| 数据 | SQLite → PostgreSQL | 先减少环境复杂度，后期再切换 |
| ORM | SQLAlchemy | 起步使用同步模式，避免过早引入异步 ORM 复杂度 |
| AI | 一个 OpenAI-compatible API + 官方 SDK | 先掌握直接调用、流式输出、错误处理 |
| 检索 | 代码文件解析 + Embedding + Chroma | MVP 优先本地跑通；后续可迁移 pgvector |
| 测试 | pytest + httpx | API 与核心业务逻辑必须有测试 |
| 工程化 | Git + Docker Compose + 结构化日志 | MVP 也必须能复现运行 |

## 四、正式开工前：环境与基础冲刺（3 周）

> 原则不是“学完所有内容再开始项目”，而是先掌握下一步必需的最小知识，再用小练习验证。每周的练习都服务于 CodeAtlas，之后可以重构或丢弃。

### 推荐开发环境

| 项目 | 推荐选择 | 原因 |
|---|---|---|
| 操作系统 | Windows + WSL2 Ubuntu | 保留 Windows 的日常使用，同时获得 Linux 开发环境；后续 Docker 与部署更顺畅 |
| 编辑器 | VS Code + Remote - WSL | 在 Windows 图形界面编辑、在 Ubuntu 中运行命令和依赖 |
| 项目位置 | `~/projects/codeatlas`（WSL 内） | 避免跨 Windows/WSL 文件系统带来的性能和权限问题 |
| Python | 3.12 或 3.13 + 每项目独立 `.venv` | 隔离依赖，避免污染全局环境 |
| 前端运行时 | Node.js LTS + npm | 用于 React + Vite 开发 |
| 浏览器 | Chrome 或 Edge | 使用开发者工具检查网络请求、页面状态和报错 |

Docker、PostgreSQL、向量数据库和云部署不在环境准备阶段安装；等项目需要时再引入。

### 第 1 周：Python 工程最小基础

**只学习这些：**

- 变量、函数、模块、`pathlib`、列表/字典；
- 文件读写、JSON、异常处理；
- 类型标注、虚拟环境、`pip`；
- `pytest` 的最基础断言与测试组织。

**小练习：**写一个命令行脚本，扫描指定代码目录，输出按扩展名统计的文件数，并将结果写入 JSON；为核心统计逻辑写 3 个测试。

**通过标准：**能独立创建/激活 `.venv`、安装依赖、运行脚本和测试。

### 第 2 周：FastAPI 与数据库最小基础

**只学习这些：**

- 路由、路径/查询参数、JSON 请求体与 Pydantic 模型；
- HTTP 状态码、异常响应；
- SQLite 和最基本的 CRUD；
- `httpx`/FastAPI 测试客户端。

**小练习：**做一个“代码仓库清单 API”，支持新增、查询、删除仓库记录；使用自动生成的 API 文档手动验证，再写 5 个接口测试。

**通过标准：**能解释一次浏览器请求如何到达 API、校验数据并返回 JSON。

### 第 3 周：React + TypeScript 最小基础

**只学习这些：**

- TypeScript 基础类型、对象、数组；
- React 组件、Props、`useState`、事件、条件渲染、列表渲染；
- `fetch` 调 API、加载/错误状态；
- 基础 CSS 布局。

**小练习：**做一个静态的“仓库卡片列表”，再接上第 2 周 API，实现新增、展示、删除仓库。

**通过标准：**能在浏览器中完成一次“输入 → 前端请求 → 后端保存 → 刷新列表”的闭环。

## 五、12 周项目驱动路线

> 本阶段在前三周基础冲刺完成后开始，适用于每周约 15–20 小时投入。若投入低于 10 小时/周，按两倍时长推进，不压缩测试与交付。

### P0：问题与骨架（第 1 周）

**学习内容**

- Python：虚拟环境、模块、文件读写、异常、类型标注。
- Git 基础工作流。
- FastAPI 路由、Pydantic 请求/响应模型。
- React：组件、Props、状态、事件、基础 TypeScript。

**交付物**

- 项目仓库、README 初稿、任务看板。
- 静态前端原型：仓库列表、目录树、代码阅读、对话四个页面/区域。
- 后端健康检查接口与前端连通。

### P1：仓库与文件闭环（第 2–3 周）

**学习内容**

- FastAPI 文件上传、表单、全局异常处理。
- ZIP 安全校验、解压与文本文件筛选。
- SQLite、SQL 基础、SQLAlchemy 模型与 CRUD。
- React 调用 API、上传进度、列表和详情状态。

**交付物**

- 上传 ZIP → 创建仓库记录 → 解析文件 → 展示目录树和代码内容。
- 数据表：Repository、SourceFile、ReadProgress。
- 至少 8 个后端测试：正常上传、非法 ZIP、超大文件、路径穿越、查询、删除等。

### P2：代码理解与对话（第 4–5 周）

**学习内容**

- LLM SDK 直接调用、提示词结构、结构化输出。
- Server-Sent Events（SSE）和流式响应。
- 任务状态、超时、重试、日志记录。
- 前端流式消息渲染与错误提示。

**交付物**

- 为仓库生成整体摘要和一级模块摘要。
- 代码问答可逐字输出。
- 数据表：ChatSession、ChatMessage、ModuleSummary。

### P3：源码引用 RAG v1（第 6–7 周）

**学习内容**

- 代码分块：按文件、函数/类边界和长度分块的取舍。
- Embedding、余弦相似度、Top-K 检索。
- 引用片段、上下文拼接、降低幻觉的提示词约束。
- 检索与生成的基础评测。

**交付物**

- 建立代码片段索引；提问时先检索后生成。
- 每个回答显示引用文件、行号范围和源码片段。
- 用自己的 WebServer 或 LevelDB 阅读材料构造 20 个真实问题，记录“是否找到正确源码”“回答是否忠实来源”。

### P4：学习体验与产品功能（第 8–9 周）

**学习内容**

- 前端信息层级、代码高亮、空状态和加载状态。
- 统计查询与轻量数据可视化。
- LLM 结构化输出的校验与降级。

**交付物**

- 阅读进度：已读文件、收藏片段、待阅读模块。
- 从已读模块生成复习问题或学习路径（二选一）。
- 面板显示仓库规模、模块数量、阅读进度和最近会话。

### P5：工程化交付（第 10–12 周）

**学习内容**

- Dockerfile、Docker Compose、环境变量与密钥管理。
- API 测试、核心前端交互测试（可选）。
- 结构化日志、请求失败排查、基础安全边界。
- README、架构图、演示与项目复盘。

**交付物**

- `docker compose up` 后可启动完整项目。
- 完整 README：功能、架构、运行方式、测试方式、限制与后续计划。
- 一段演示视频或 GIF：导入仓库 → 查看模块 → 带引用问答 → 学习进度。
- 一份真实评测/性能记录，不编造指标。

## 七、学习与执行规则

### 每周自检

1. 本周是否产生一个可运行、可演示或可测试的交付物？
2. 本周新增的知识，是否已经进入项目代码？
3. 是否在做 MVP 范围外的“看起来高级”的事情？若是，记录到 Backlog，不立即实现。
4. 是否写了测试、README 或复盘，而不只是增加了功能？

### 每日建议节奏

```
主开发：2–3 小时
学习/查阅文档：30–60 分钟（只解决当前项目问题）
复盘与提交：15 分钟
```

### C++ 的位置

- 前 6 周不新增 C++ 大模块学习。
- 后续每周最多 2–3 小时，用于复盘 WebServer 或阅读 LevelDB。
- C++ 项目可作为 CodeAtlas 的首批真实测试仓库；不与 AI 主线争夺注意力。

## 八、完成标准

完成不是“写完所有功能”，而是同时满足：

- [ ] 一个陌生代码仓库能被安全导入并浏览。
- [ ] 用户可以查看仓库/模块摘要。
- [ ] 用户的代码问题能得到流式回答，并看到明确源码引用。
- [ ] 核心流程具备自动化测试。
- [ ] 项目可用 Docker 启动，且说明文档让他人能复现。
- [ ] 有真实案例、演示和诚实的限制说明。

达成后，再根据真实使用反馈决定：继续做代码依赖图/学习路径，还是转向下一阶段的 AI 平台、检索优化或求职准备。
