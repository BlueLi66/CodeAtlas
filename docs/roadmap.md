# CodeAtlas — AI 应用全栈学习路线

> 建立：2026-09-18  
> 当前阶段：大三上  
> 方向：AI 应用全栈工程（以可见、可交互的产品为中心）  
> 核心项目：**CodeAtlas — 代码库学习导航器**

---

## 一、路线选择

### 当前背景（只保留已确认信息）

- 计算机专业，大三上。
- 已学习操作系统、计算机网络、数据库的基础知识。
- 接触过 C++ WebServer 和 LevelDB；它们是后续学习与验证素材，但不作为当前主线项目或默认的已掌握能力。
- Python 处于入门阶段。
- 挑战杯项目已停止；没有 Dify 开源贡献。
- 更喜欢能看见结果、能直接感受到功能变化的开发工作。

### 为什么选择 AI 应用全栈

目标不是成为“只会调用模型 API 的人”，而是能够把 AI 能力做成可靠、可使用的产品：前端交互、后端服务、数据管理、检索、模型调用、测试与部署缺一不可。

这条路线具备两个优势：

1. **反馈快**：每周都会有页面、交互或产品能力的可见变化。
2. **可持续扩展**：后续可向 AI 平台、LLM 服务工程、检索系统，甚至推理部署延伸；已有的 C++/系统基础可成为差异化，而不必和主线竞争时间。

### 近期原则

```
单主线：CodeAtlas 项目驱动学习
先产品闭环，后高级能力
先直接 SDK 与基本原理，后框架封装
先可测试、可部署，后复杂功能
```

## 二、项目定义：CodeAtlas

### 一句话描述

CodeAtlas 帮助开发者理解陌生代码仓库：导入仓库后查看目录与代码、了解模块职责，并对代码提问；每个回答都应定位到具体源码片段。

### 目标用户

- 正在阅读陌生项目的学生或初级开发者。
- 希望系统梳理自己历史项目的开发者。

### 核心价值

不是泛泛地“和代码聊天”，而是提供：

- 仓库结构与模块职责的清晰概览；
- 有来源定位的代码问答；
- 可追踪的代码阅读与学习进度。

### MVP 范围（必须完成）

1. 上传 ZIP 格式的代码仓库。
2. 解析安全允许的文本源文件，展示目录树与文件内容。
3. 自动生成仓库概览和模块摘要。
4. 针对当前仓库提问，流式显示回答，并列出引用的文件与片段。
5. 保存仓库、文件元数据、对话和阅读进度。
6. 用 Docker Compose 一键启动，并有基础测试与 README。

### 明确不做（第一版）

- 自动修改或执行代码；
- 自动修复 Bug；
- 多 Agent；
- 多模型提供商切换；
- 完整调用图、复杂 AST 分析；
- 多人协作、权限体系、云端同步；
- Kubernetes、CUDA、推理引擎。

### 后续候选功能（仅在 MVP 完成后选择）

- Python/C++ 符号提取与轻量依赖图；
- “建议先读哪些文件”的学习路径；
- 基于仓库的面试题和复习卡片；
- 代码阅读笔记与待复习列表；
- 混合检索、检索评测与缓存。

## 三、最小技术栈

| 层级 | 技术 | 当前取舍 |
|---|---|---|
| 前端 | TypeScript + React + Vite | 优先建立可见交互；先不使用复杂状态库或 SSR |
| 后端 | Python + FastAPI + Pydantic | REST API、文件上传、流式响应 |
| 数据 | SQLite → PostgreSQL | 先减少环境复杂度，后期再切换 |
| ORM | SQLAlchemy | 起步使用同步模式，避免过早引入异步 ORM 复杂度 |
| AI | 一个 OpenAI-compatible API + 官方 SDK | 先掌握直接调用、流式输出、错误处理 |
| 检索 | 代码文件解析，按需加入 Embedding + Chroma | 先验证选中文件和简单检索的基线；需要跨文件检索时再引入向量库 |
| 测试 | pytest + httpx | API 与核心业务逻辑必须有测试 |
| 工程化 | Git + Docker Compose + 结构化日志 | MVP 也必须能复现运行 |

## 四、正式开工前：环境与基础冲刺（3 周）

> 原则不是“学完所有内容再开始项目”，而是先掌握下一步必需的最小知识，再用小练习验证。每周的练习都服务于 CodeAtlas，之后可以重构或丢弃。

### 推荐开发环境

| 项目 | 推荐选择 | 原因 |
|---|---|---|
| 操作系统 | Windows + WSL2 Ubuntu | 保留 Windows 的日常使用，同时获得 Linux 开发环境；后续 Docker 与部署更顺畅 |
| 编辑器 | VS Code + Remote - WSL | 在 Windows 图形界面编辑、在 Ubuntu 中运行命令和依赖 |
| 项目位置 | `~/projects/codeatlas`（WSL 内） | 避免跨 Windows/WSL 文件系统带来的性能和权限问题 |
| Python | 3.12 或 3.13 + 每项目独立 `.venv` | 隔离依赖，避免污染全局环境 |
| 前端运行时 | Node.js LTS + npm | 用于 React + Vite 开发 |
| 浏览器 | Chrome 或 Edge | 使用开发者工具检查网络请求、页面状态和报错 |

Docker、PostgreSQL、向量数据库和云部署不在环境准备阶段安装；等项目需要时再引入。

### 第 1 周：Python 工程最小基础

**只学习这些：**

- 变量、函数、模块、`pathlib`、列表/字典；
- 文件读写、JSON、异常处理；
- 类型标注、虚拟环境、`pip`；
- `pytest` 的最基础断言与测试组织。

**小练习：**写一个命令行脚本，扫描指定代码目录，输出按扩展名统计的文件数，并将结果写入 JSON；为核心统计逻辑写 3 个测试。

**通过标准：**能独立创建/激活 `.venv`、安装依赖、运行脚本和测试。

### 第 2 周：FastAPI 与数据库最小基础

**只学习这些：**

- 路由、路径/查询参数、JSON 请求体与 Pydantic 模型；
- HTTP 状态码、异常响应；
- SQLite 和最基本的 CRUD；
- `httpx`/FastAPI 测试客户端。

**小练习：**做一个“代码仓库清单 API”，支持新增、查询、删除仓库记录；使用自动生成的 API 文档手动验证，再写 5 个接口测试。

**通过标准：**能解释一次浏览器请求如何到达 API、校验数据并返回 JSON。

### 第 3 周：React + TypeScript 最小基础

**只学习这些：**

- TypeScript 基础类型、对象、数组；
- React 组件、Props、`useState`、事件、条件渲染、列表渲染；
- `fetch` 调 API、加载/错误状态；
- 基础 CSS 布局。

**小练习：**做一个静态的“仓库卡片列表”，再接上第 2 周 API，实现新增、展示、删除仓库。

**通过标准：**能在浏览器中完成一次“输入 → 前端请求 → 后端保存 → 刷新列表”的闭环。

## 五、12 周项目驱动路线

> 本阶段在前三周基础冲刺完成后开始。周数是每周约 15–20 小时投入时的估计，不是赶进度的截止日期；投入较少时顺延，以每阶段的功能与理解验收为准。

### P0：问题与骨架（第 1 周）

**学习内容**

- 复用前三周已练习的 Python、Git、FastAPI 和 React 基础，不重复从头学一遍。
- 梳理“页面操作 → 请求 → 后端 → 数据 → 页面更新”的数据流，以及各区域未来要展示的信息。

**交付物**

- 项目仓库、README 初稿、任务看板。
- 静态前端原型：仓库列表、目录树、代码阅读、对话四个页面/区域。
- 后端健康检查接口与前端连通。

**通过标准：**能指出每个区域当前的数据来源，区分静态示例与真实 API 数据，并解释健康状态如何出现在页面上。

### P1：仓库与文件闭环（第 2–3 周）

**学习内容**

- 先补后端依赖清单、启动与建表说明，验证从新环境可以运行当前项目。
- FastAPI 文件上传；ZIP 的大小、格式、路径和文件类型安全校验。
- 按需要学习 SQLAlchemy 文件模型和查询，以及 React 的上传、列表、文件选择状态。

**交付物**

- 分步完成：安全接收 ZIP → 创建仓库并保存允许的文件信息 → 展示真实目录树 → 点击文件查看内容。
- 数据表先覆盖 Repository 与 SourceFile；ReadProgress 留到 P4。设计上传接口时确认 ZIP 导入没有来源网址时如何表示，不能沿用当前必填的 `source_url` 假设。
- 为关键行为写测试：正常上传、非法 ZIP、大小限制、路径穿越、文件筛选、查询等；按风险覆盖，不凑固定数量。

**通过标准：**能用一个小 ZIP 演示从上传到阅读文件的完整流程，并解释每一步的数据去向与失败处理。

### P2：代码理解与对话（第 4–5 周）

**学习内容**

- 从“针对一个选中文件提问”入手，学习 SDK 调用、提示词、上下文和回答依据。
- 基本问答跑通后，再学习 SSE 流式响应、错误提示、摘要与必要的超时处理。

**交付物**

- 先完成选中文件的问答，并展示回答所依据的文件或片段；再增加逐字输出和仓库、一级模块摘要。
- 为保存对话增加 ChatSession、ChatMessage；ModuleSummary 随摘要功能增加，避免一次建齐却没有使用场景。

**通过标准：**能说明发送给模型的文件内容来自哪里，并在回答缺少依据时明确指出限制。

### P3：源码引用 RAG v1（第 6–7 周）

**学习内容**

- 代码分块：按文件、函数/类边界和长度分块的取舍。
- 先用少量真实问题检验直接提供文件内容的基线，再学习 Embedding、余弦相似度和 Top-K 检索。
- 引用片段、上下文拼接、降低幻觉的提示词约束。
- 检索与生成的基础评测。

**交付物**

- 建立代码片段索引；提问时先检索后生成。
- 每个回答显示引用文件、行号范围和源码片段。
- 先用少量真实问题检查检索与引用，再逐步扩充到 20 个 WebServer 或 LevelDB 问题，记录“是否找到正确源码”“回答是否忠实来源”。

### P4：学习体验与产品功能（第 8–9 周）

**学习内容**

- 前端信息层级、代码高亮、空状态和加载状态。
- 统计查询与轻量数据可视化。
- LLM 结构化输出的校验与降级。

**交付物**

- 增加 ReadProgress，并实现已读文件记录；收藏片段、待阅读模块按实际使用反馈选择。
- 面板显示必要的仓库规模、阅读进度和最近会话信息。
- 复习问题、学习路径与更细的统计留在 MVP 后候选功能中。

### P5：工程化交付（第 10–12 周）

**学习内容**

- Dockerfile、Docker Compose、环境变量与密钥管理。
- 在已有关键行为测试上补齐遗漏场景；核心前端交互测试按需要增加。
- 结构化日志、请求失败排查、基础安全边界。
- 完善已逐步维护的 README，再制作架构图、演示与项目复盘。

**交付物**

- `docker compose up` 后可启动完整项目。
- 完整 README：功能、架构、运行方式、测试方式、限制与后续计划。
- 一段演示视频或 GIF：导入仓库 → 查看模块 → 带引用问答 → 学习进度。
- 一份真实评测/性能记录，不编造指标。

## 七、学习与执行规则

### 每周自检

1. 本周是否产生一个可运行、可演示或可测试的交付物？
2. 本周新增的知识，是否已经进入项目代码？
3. 是否在做 MVP 范围外的“看起来高级”的事情？若是，记录到 Backlog，不立即实现。
4. 是否能独立解释一次数据流，并对已完成的功能做一个小变化？
5. 是否为关键行为补了必要的测试、运行说明或复盘？

每次以一个可解释、可验证的小功能为单位：先讲清问题与数据流；新概念详细学习，已练过的写法直接复用；完成后做与风险相称的验证，并尝试独立修改一个小变化。测试数量和敲代码行数都不作为理解程度的替代指标。

### 每日建议节奏

```
主开发：2–3 小时
学习/查阅文档：30–60 分钟（只解决当前项目问题）
复盘与提交：15 分钟
```

### C++ 的位置

- 前 6 周不新增 C++ 大模块学习。
- 后续每周最多 2–3 小时，用于复盘 WebServer 或阅读 LevelDB。
- C++ 项目可作为 CodeAtlas 的首批真实测试仓库；不与 AI 主线争夺注意力。

## 八、完成标准

完成不是“写完所有功能”，而是同时满足：

- [ ] 一个陌生代码仓库能被安全导入并浏览。
- [ ] 用户可以查看仓库/模块摘要。
- [ ] 用户的代码问题能得到流式回答，并看到明确源码引用。
- [ ] 核心流程具备自动化测试。
- [ ] 项目可用 Docker 启动，且说明文档让他人能复现。
- [ ] 有真实案例、演示和诚实的限制说明。

达成后，再根据真实使用反馈决定：继续做代码依赖图/学习路径，还是转向下一阶段的 AI 平台、检索优化或求职准备。
